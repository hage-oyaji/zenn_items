# 2026年9月 AIハーネストレンドTOP10  
## モデル性能の次に勝敗を決める「Harness Engineering」の現在地

> **調査基準日：2026年9月3日**  
> 対象：AI Coding / AI Agent / Harness Engineering  
> 評価軸：技術的インパクト、成熟度、SIerでの実用性、今後の伸び

2026年9月現在、AI開発の面白さは「どのLLMが一番賢いか」だけではなくなっている。

むしろ私が注目しているのは、

**そのモデルを、どう働かせるか。**

という部分だ。

同じモデルを使っていても、

- 何をContextに入れるか
- どのToolを使わせるか
- どのSkillを読み込ませるか
- どこまで自律実行させるか
- 失敗をどう検知するか
- 何を記憶させるか
- どのタイミングで別Agentへ仕事を渡すか

によって、最終的な性能は大きく変わる。

このモデル外側の実行基盤を、ここでは**AI Harness**と呼ぶ。

2026年2月、OpenAIはこれを明確に「Harness Engineering」と呼び、Codexを使った実験で、コード、テスト、CI、ドキュメント、ObservabilityまでAgentに作らせる開発スタイルを公開した。人間の仕事は「コードを書くこと」から「Agentが仕事を完了できる環境を作ること」へ移っている。

そして2026年7月、Claude Code、Codex CLI、Gemini CLI、OpenHands、Aiderなど11種類の実用Coding Harnessをソースコードから分析した研究が公開された。

ここで非常に興味深い結果が出ている。

**11製品中、一般的なAgent Frameworkを内部Runtimeとして利用しているものはゼロ。**

さらに、

- Skills：9 / 11
- MCP：8 / 11
- Vector Embeddingによるコード検索：0 / 11

だった。

この結果はかなり象徴的だ。

2024〜2025年に想像されていた、

> 巨大なAgent Frameworkの中に大量のAgentを配置する

という方向とは少し違う。

2026年9月の本流はむしろ、

> **シンプルなAgent Loopを中心に、Context、Skills、Tools、Sandbox、Memory、Verificationを高度化する**

方向へ向かっている。

今回はその中でも、今追いかける価値が高い10のトレンドを評価する。

# 1位：Context Engineering + Retrieval Harness

### 熱くなった時期
**2026年2月〜9月**

### 評価
**5.0 / 5**

AI Harnessを一つだけ勉強するなら、私はまずContext Engineeringを選ぶ。

理由は単純で、

> **モデルは、Contextに存在しないことを正しく判断できない。**

からだ。

しかし、

「全部Contextへ入れればいい」

でもない。

ここが難しい。

---

## 100万Contextは問題を解決しなかった

現在の上位モデルでは100万トークン級のContextが珍しくなくなっている。

それでも、

```text
README
設計書
ソースコード
ログ
チケット
過去の会話
テスト結果
コーディング規約
Skill
Tool定義
Memory
```

を全部突っ込む設計は良くない。

情報量が増えるほど、

**重要な情報が埋もれる。**

さらに、

- Token Cost
- Latency
- Cache効率
- Instruction conflict

にも悪影響が出る。

だから重要なのはContext Windowのサイズではない。

**Context Selectionの品質**

だ。

---

## 2026年型はProgressive Disclosure

OpenAIのHarness Engineeringでも象徴的な失敗が紹介されている。

最初は巨大な`AGENTS.md`にAgentが必要とする情報を全部書こうとした。

しかし最終的には、

```text
AGENTS.md
    ↓
Architecture
    ↓
Domain docs
    ↓
Plans
    ↓
Reference
```

という形に変更した。

つまり`AGENTS.md`は百科事典ではなく、

**地図**

にする。

AnthropicのSkillsにも同じ思想がある。

Metadataだけ常時見せておき、詳細なInstructionやResourceは必要になった時点で読み込む。

Anthropicはこれを明確に**Progressive Disclosure**として説明している。

---

## さらに面白いのがRetrieval

2026年7月のHarness研究では、分析した11 Coding Harnessのすべてで、

**コード検索にVector Embeddingを使っていなかった。**

代わりに、

```text
grep
filesystem
git
symbol search
repository map
AST
```

などの決定論的検索を使っている。

これは結構重要だ。

数年前なら、

> 「Agentを作るならまずVector DB」

という設計が多かった。

しかしCoding Agentでは、

> **ファイル名やシンボルを正確に検索できるなら、普通の検索の方が強い**

ケースが多い。

---

## 素晴らしいところ

モデルを変更しなくても性能が上がる。

これは大きい。

例えば、

```text
GPT-5.6 Sol
Context設計：悪い
```

より、

```text
GPT-5.6 Terra
Context設計：良い
```

の方が、特定の実務では良い結果になる可能性がある。

Context Engineeringは、

**モデル性能を増幅するレバレッジ**

だからだ。

---

## 注意点

最大の問題は、

**Contextを削りすぎること。**

AgentがArchitecture Decisionを知らないままコードを書くと、局所的には正しくてもシステム全体では間違った実装になる。

したがってRetrievalそのものにも、

- Recall
- Precision
- Retrieval latency
- Context utilization

の評価が必要になる。

### SIer視点

★★★★★

特に大規模既存システムでは最重要。

数百万行のコードを丸ごとモデルへ入れるのではなく、

**必要なコード・設計・過去の判断をどう発見させるか**

が競争力になる。

---

# 2位：Agent Skills

### 熱くなった時期
**2026年5月〜9月**

### 評価
**5.0 / 5**

Skillsは2026年のHarnessトレンドの中でも、特にSIerと相性がいい。

Skillとは簡単に言えば、

> **Agentが必要になったときだけ読み込める、再利用可能な仕事のやり方**

だ。

Anthropicでは基本的に、

```text
skill-name/
 ├ SKILL.md
 ├ scripts/
 ├ references/
 └ templates/
```

というFilesystemベースの構造を取れる。

Claude Codeでは`.claude/skills/`に配置すると自動検出される。

---

## Promptとの違いは大きい

例えばOracle → PostgreSQL移行を考える。

巨大なPromptに、

```text
Oracleの空文字はNULLです
CHARの扱いに注意してください
NEXT_DAYを変換してください
INSTRを確認してください
Synonymは...
```

と毎回書くのは辛い。

Skillなら、

```text
skills/
 └ oracle-to-postgresql/
       ├ SKILL.md
       ├ conversion-rules.md
       ├ check.sql
       └ validate.py
```

として保存できる。

Agentは必要になったときだけロードする。

さらにSkillには文章だけでなく、

**Scriptを持たせられる。**

ここが重要だ。

---

## 「知識」から「能力」へ

RAGは基本的に、

> この情報を読んでください。

だ。

Skillは、

> **このやり方で仕事をしてください。**

になる。

私はこの差をかなり大きいと考えている。

SIerが長年蓄積してきた、

- Oracle移行ノウハウ
- Java開発標準
- AWS設計基準
- Security Review
- 障害調査
- Release判定
- 顧客固有ルール

をSkill化すれば、

**会社のKnow-howをAgent Capabilityへ変換できる。**

---

## 2026年7月時点で既にかなり広がっている

11種類のCoding Harnessを比較した研究では、

**9 / 11がSKILL.md形式のSkillsを採用していた。**

つまりSkillsはClaude固有機能として見るより、

**Agent Harnessにおける共通設計パターン**

になり始めていると考えた方がいい。

---

## 素晴らしいところ

企業固有の差別化ポイントを作れる。

LLMは競合企業も買える。

しかし、

```text
自社のSkill Library
```

は競合企業にはない。

したがって、

> **モデルはコモディティ化してもSkill Libraryは企業資産として残る**

可能性がある。

---

## 注意点

Skillを増やせば増やすほど良いわけではない。

500個のSkillがあった場合、

**どれを選択するのか**

という別の問題が出てくる。

さらにSkillにはCode Executionを含められる。

Anthropicも、信頼できないSkillはTool misuseやData exposureを引き起こす可能性があるため、Softwareをインストールするのと同じように扱うべきだとしている。

### SIer視点

★★★★★

個人的には、

**今から会社単位でSkill Libraryを作り始めてもいい**

と思っている。

---

# 3位：Verification / Eval Loop

### 熱くなった時期
**2026年1月〜9月**

### 評価
**5.0 / 5**

AI Agentで最も危険な設計の一つが、

```text
Agent:
実装しました。完了です。
```

で仕事を終了させることだ。

Agent自身に「完成」を判断させてはいけない。

---

## 2026年型Agentの基本Loop

理想はこうなる。

```text
Plan
 ↓
Implement
 ↓
Build
 ↓
Test
 ↓
Observe
 ↓
Evaluate
 ↓
Fix
 ↓
Test
 ↓
Done
```

これがVerification Loopだ。

Anthropicも2026年1月、Agent Evalsについて、単一の最終回答ではなく、

**複数Turn、Tool Call、State Changeを含むAgent全体を評価する**

必要性を強調している。

---

## LLM Judgeだけでは足りない

例えば、

```text
Reviewer Agent:
このコードは問題ありません。
```

だけでは弱い。

できるだけ、

```text
Compiler
Unit Test
Integration Test
E2E
Schema Validation
Static Analysis
Security Scan
Architecture Test
```

のような**決定論的Verifier**を使うべきだ。

LLMが得意なのは、

「良さそうか」

という判断。

Compilerが得意なのは、

「コンパイルできるか」

という判定。

それぞれに仕事を分ける。

---

## 2026年9月には「HarnessをHarnessで改善する」研究まで出てきた

2026年9月1日に公開されたHarness-of-Harness研究では、

既存Coding Harnessをさらに外側から、

```text
Planning
 ↓
Coding
 ↓
Testing
 ↓
Evaluation
 ↓
Next iteration
```

というLoopで回している。

3回のIterationで、対象Harnessに対して平均52.25%の相対改善を報告している。

まだ研究段階ではあるが、方向性は非常に面白い。

モデルを変えるのではなく、

**HarnessがAgentの仕事を繰り返し改善する。**

---

## 素晴らしいところ

80点のモデルでも、

```text
80
 ↓ Test
90
 ↓ Review
94
 ↓ Regression Test
96
```

のようにSystemとして精度を上げられる。

つまり、

**Accuracyをモデル会社だけに依存しなくなる。**

### 注意点

テストそのものが間違っていれば意味がない。

さらにAgentが自分でTestを書き、自分でImplementationを書き、自分でReviewすると、

同じ誤解を共有する可能性がある。

Independent Evaluatorを持つ価値は大きい。

### SIer視点

★★★★★

SIerがAgent導入で最も投資すべき部分の一つ。

---

# 4位：Isolated Sandbox + Git Worktree

### 熱くなった時期
**2026年2月〜9月**

### 評価
**4.9 / 5**

Agentを強くすると必ずぶつかる問題がある。

**権限だ。**

Agentには、

```text
git
npm
maven
docker
filesystem
network
cloud
database
```

を使わせたい。

しかし全部許可するのは危険。

---

## ApprovalではなくIsolation

初期のCoding Agentでは、

```text
このCommandを実行してよいですか？
```

と毎回人間に確認していた。

ところがこれは非常に効率が悪い。

しかもApproveが何十回も出ると、

**Approval Fatigue**

が発生する。

AnthropicではSandbox導入によって、内部利用時のPermission Promptを84%削減したとしている。

発想は、

> 一つ一つ許可する

ではなく、

> **安全な箱の中なら自由に動いてよい**

へ変わる。

---

## Worktreeとの組み合わせ

2026年2月に公開されたCodex Appでは、複数Agentの並列実行に加え、分離されたGit Worktreeが重要な機能として組み込まれた。

例えば、

```text
Agent A
worktree/feature-a

Agent B
worktree/feature-b

Agent C
worktree/test
```

とする。

3 Agentが同じRepositoryを同時に触っても衝突しにくい。

---

## 素晴らしいところ

Sandbox + Worktreeは、

**AutonomyとSecurityを同時に上げられる**

数少ない設計だ。

これは非常に強い。

---

## 注意点

Sandboxがあるから安全、ではない。

特に、

```text
AWS Credential
GCP Service Account
GitHub Token
Production DB
Docker Socket
Internal Network
```

をSandbox内へ渡してしまえば意味が薄れる。

2026年5月にOpenAIが公開したCodexの社内運用でも、Sandbox、Approval Policy、Network Policy、Telemetryを組み合わせている。

### SIer視点

★★★★★

本番システムへAgentを入れるなら、ほぼ前提条件。

---

# 5位：Programmatic Tool Calling

### 熱くなった時期
**2026年7月〜9月**

### 評価
**4.9 / 5**

個人的に、2026年後半でもっとも面白いトレンドの一つ。

従来のAgentは、

```text
LLM
 ↓
Tool
 ↓
LLM
 ↓
Tool
 ↓
LLM
 ↓
Tool
```

だった。

しかしToolが100回必要なら、100回Modelを経由する。

当然、

- Token
- Latency
- Cost

が増える。

---

## 2026年7〜8月に構造が変わった

GPT-5.6ではProgrammatic Tool Callingが導入され、

**モデル自身がJavaScriptを書き、そのProgramから複数Toolを呼べる**

ようになった。

つまり、

```text
LLM
 ↓
Program
 ├ Tool A
 ├ Tool B
 ├ Tool C
 ├ Filter
 ├ Join
 └ Aggregate
 ↓
LLM
```

にできる。

---

## これは地味に革命的

例えば100件のログを検索する。

従来なら、

```text
100件
 ↓
全部LLM Context
 ↓
LLMが読む
```

だった。

Programmatic Tool Callingなら、

```text
100件
 ↓
Programでfilter
 ↓
errorだけ抽出
 ↓
10件
 ↓
LLM
```

にできる。

LLMは、

**判断が必要なところだけ使う。**

---

## 素晴らしいところ

AI Harnessの中へ、

**普通のProgrammingが戻ってくる。**

これが良い。

SortはLLMにやらせない。

FilterもLLMにやらせない。

JSON ValidationもLLMにやらせない。

コードで100%正しくできることはコードに任せる。

モデルには曖昧な判断だけ任せる。

---

## 注意点

すべてをProgrammaticにすると逆効果。

Tool Aの結果によって、

「次に何を調べるか」

を推論する必要があるケースはModel Loopの方が向いている。

OpenAIも、Programmatic Tool CallingをTool-heavyで途中の各Stepに新たなモデル判断が不要なWorkflow向けとしている。

### SIer視点

★★★★★

大量データを扱う業務Agentではかなり重要になる。

---

# 6位：MCP ― Tool Callingから「Agentの共通I/O」へ

### 熱くなった時期
**2026年5月〜8月**

### 評価
**4.8 / 5**

MCPはもう単なる流行Protocolとして扱わない方がいい。

2026年7月28日の新仕様では、

- Stateless core
- Header-based routing
- Cacheable tool list
- Multi Round-Trip Requests
- Authorization強化
- Extensions
- Tasks

などが追加された。

特にStateless化は大きい。

普通のHTTP Infrastructure上へ、

Remote MCP Serverをかなり置きやすくなる。

---

## 2026年8月時点では規模も大きい

MCPプロジェクトによると、Tier 1 SDK全体で月間約5億Downloadに近づき、TypeScript / Python SDKはそれぞれ累計10億Downloadを超えたという。

Coding Harness研究でも、

**11中8製品がMCP対応**

だった。

少なくともAgent Tool Interfaceの有力標準であることは間違いない。

---

## SIerにとって本当に重要な部分

例えば社内には、

```text
GitHub
Backlog
Jira
Oracle
PostgreSQL
AWS
GCP
ServiceNow
社内API
ログ基盤
```

がある。

Claude用Connector。

GPT用Connector。

Gemini用Connector。

を全部別々に作りたくない。

理想は、

```text
          Claude
             │
GPT ───── MCP Layer ───── Gemini
             │
       Internal Systems
```

だ。

### 素晴らしいところ

**Tool LayerでModel Vendor Lock-inを弱められる。**

SIerにとってかなり価値がある。

### 注意点

MCP Serverに強い権限を付けすぎると、

中央集権的な巨大Attack Surfaceになる。

Tool Catalogが100、200と増えればTool Selectionも難しくなる。

### SIer視点

★★★★★

社内AI Platformを作るなら、標準候補として検討する価値が高い。

# 7位：Multi-Agent / Subagents

### 熱くなった時期
**2026年7月〜9月**

### 評価
**4.5 / 5**

派手さだけなら1位。

しかし私は7位に置く。

理由は、

**強力だが、使い方を間違えやすい**

からだ。

---

## 2026年8月にさらに本格化

GPT-5.6ではMulti-agentがResponses APIのBetaとして提供され、一つのモデルが複数Subagentを並列実行し、結果を統合できるようになった。

`ultra`ではデフォルト4 Agentを並列実行し、並列度を増やすことで一部BenchmarkのScore / Latency frontierが改善したとOpenAIは報告している。

2026年8月にはAnthropicも、今後Agent同士のInteractionが急増するとしてMulti-Agent Systemの問題を研究対象としている。

---

## ではAgentは細かく分けるべきか？

私はそうは思わない。

例えば、

```text
Java Agent
Spring Agent
SQL Agent
AWS Agent
Test Agent
Security Agent
```

と細かく切る。

一見合理的だ。

しかし実際には、

```text
Java → Spring
Spring → DB
DB → Java
Java → Test
Test → Java
```

とContext Transferが大量に発生する。

結果として、

- Token増加
- Latency増加
- Context Loss
- Coordination Error

が起きる。

---

## Agentを分ける基準

「専門分野が違うから」

ではない。

私は、

> **Contextを分離する価値があるか**

で判断する方がいいと思う。

例えば、

```text
10個の独立Moduleを調査
20件のPRを同時Review
市場を10方向から調査
5種類の設計案を並行検証
```

はMulti-Agentと非常に相性がいい。

逆に一つの巨大なTransaction処理を、

5 Agentで分割実装するのは難しい。

---

## 素晴らしいところ

並列化できる仕事なら、

**Wall Clock Timeを大幅に短縮できる。**

人間でいう、

「10人で同時に調べる」

をソフトウェアとして実現できる。

---

## 注意点

Token消費は当然増える。

さらにManager Agent自体がボトルネックになる。

Multi-Agentは、

**性能向上機能ではなくCompute投資機能**

と考えた方がいい場合もある。

### SIer視点

★★★★☆

全タスクMulti-Agentではなく、Research・Migration・Reviewなど並列性が高い領域から使うのがよい。

---

# 8位：Memory + Repository Knowledge

### 熱くなった時期
**2026年2月〜9月**

### 評価
**4.7 / 5**

Long Contextが大きくなったからMemoryはいらない。

これは違う。

ContextとMemoryは役割が異なる。

Contextは、

**今考えるための情報。**

Memoryは、

**過去の仕事から学習した情報。**

だ。

---

## Memoryも全部ロードしない

OpenAI Agents SDKのSandbox Memoryでは、

```text

MEMORY.md
raw_memories
rollout_summaries
```

のような階層を持つ。

まず小さなSummaryを見せ、必要な場合だけ詳細Memoryを探索できる。

これもProgressive Disclosureだ。

---

## CodingではRepository自体がMemoryになる

OpenAIのHarness Engineeringで特に興味深い考え方がこれだ。

Slack。

Google Docs。

人間の頭。

ここに重要情報が存在してもAgentは安定して参照できない。

そこで、

```text
Architecture
Decision
Plan

```

をRepositoryへ置く。

Repositoryを**System of Record**にする。

これは企業開発ではかなり強い。

---

## 素晴らしいところ

Gitで管理できる。

つまりKnowledgeにも、

```text
version

review
history
ownership
CI
```

を適用できる。

「設計書がSharePointにあるが、どれが最新版か分からない」

という世界よりAgent Friendlyだ。

---

## 注意点

Memoryは腐る。

古いMemoryを信じると、Agentは現在のコードより過去の知識を優先してしまう。

Memoryには必ず、

**Forget / Update / Validation**

が必要になる。

### SIer視点

★★★★★

# 9位：Prompt Caching / Context Economics

### 熱くなった時期
**2026年7月〜9月**

### 評価
**4.7 / 5**

Prompt Cachingを単なるAPI料金節約機能として見ると、重要性を過小評価する。

Agent Harnessでは、

```text
System Prompt
Tool definitions
Skills metadata
Repository rules
Architecture
Conversation
```

を何度も繰り返しモデルへ渡す。

つまりContextそのものが、

**Infrastructure Cost**

になる。

---

## GPT-5.6でさらにHarness寄りになった

GPT-5.6ではExplicit Prompt Cachingが入り、

どのPrefixをCacheさせるかを明示的に設計できるようになった。

最大4つの明示的Breakpointを指定できる。

GPT-5.6ではCache Readは通常Inputより90% Discountされる一方、Cache Writeには1.25倍の料金が掛かる。

つまり、

> Cacheすれば必ず安い

ではない。

---

## Harness側の設計問題になる

例えば、

```text
System
Tools
Skills
Repository Rules
```

を頻繁に並べ替えるHarnessではCache Hitしにくい。

逆に、

```text
Stable Prefix
        ↓
Dynamic Context
        ↓
User Task
```

という構造にすればCacheを効かせやすい。

OpenAIもGPT-5.6のEfficiency解説で、Context bloatを避け、Cache可能なPrefixを保つことをHarness側の重要な工夫として説明している。

---

## 素晴らしいところ

Context Architectureの改善が、

- Cost
- Latency
- Throughput

の全部に効く。

Agentを100人、1000人相当動かす世界ではかなり重要になる。

### 注意点

Cache Hit率を見ずに設計すると逆に高くなる可能性がある。

これからは、

```text
tokens
cached_tokens
cache_write_tokens
cost/task
```

までObservabilityに入れたい。

### SIer視点

★★★★★

大量Agent利用を想定するなら早めに設計した方がよい。

# 一番大きな変化は「LLMに全部やらせない」こと

この10個を見ていて、私は一つの共通点があると思う。

それは、

> **LLMに任せる範囲を増やすのではなく、LLMが得意な部分だけを任せる**

方向へ進んでいることだ。

例えば、

### 検索

LLMではなくRetrieval Harness。

### 手順

巨大PromptではなくSkills。

### Filter / Join

LLMではなくProgram。

### 安全性

LLMの自制心ではなくSandbox。

### 正しさ

LLMの自己評価ではなくTest。

### 永続知識

Contextに全部積むのではなくMemory / Repository。

### 外部システム

個別実装ではなくMCP。

つまりHarness Engineeringとは、

**LLMを万能化する技術ではない。**

むしろ、

> **LLMを万能だと思わなくても、高品質な仕事ができるシステムを作る技術**

なのだと思う。

# 結論：2026年9月、AIの競争は「IQ」から「仕事の設計」へ移っている

2025年までは、

**どのモデルが一番賢いか**

を追っていればよかった。

2026年9月現在、それだけでは足りない。

見るべきものは、

**Model**

ではなく、

**Model × Harness**

だ。

そして今のトレンドを見ると、優れたHarnessは必ずしも巨大ではない。

むしろ、

```text
Small Agent Loop

+ Good Context
+ Skills
+ Deterministic Tools
+ MCP
+ Sandbox
+ Memory
+ Verification
+ Cache
+ Selective Multi-Agent
```

という構造へ収束しつつある。

モデルには、

**曖昧な判断**

を任せる。

プログラムには、

**決定論的な処理**

を任せる。

Sandboxには、

**安全性**

を任せる。

Testには、

**正しさ**

を任せる。

Repositoryには、

**組織知**

を任せる。

Skillsには、

**仕事のやり方**

を任せる。

そしてHarnessが、それら全部を接続する。

私は2026年9月時点のAI Engineeringを一言で表すなら、こう考えている。

> **LLMの性能を競うフェーズから、LLMが最高の仕事をできる環境を設計するフェーズへ。**

これが、今起きているHarness Engineeringの本質ではないだろうか。
